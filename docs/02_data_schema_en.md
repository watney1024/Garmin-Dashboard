# 02 · Data formats & schemas (for AI agents)

This document defines the data-file formats used in the workspace/repo. **Once a format
is agreed it becomes a contract — change the code and the docs together.** When handling
data, follow this document exactly.

## 1. Master table `Activities.csv` (canonical 16 columns)

The full activity table, rebuilt weekly from Garmin by `scripts/garmin_pull.py`. Purpose:
completeness check + title store + fast trends (weekly volume / sessions / time / HR).

Header is **verbatim** (Chinese column names, `utf-8-sig` = BOM):

```csv
活动类型,类型Key,日期,标题,距离km,时长,移动时长,平均配速min/km,热量,平均心率,最大心率,步数,累计爬升m,累计下降m,事件类型,活动ID
```

| Column | Meaning | Rule |
|---|---|---|
| 活动类型 | Chinese type name | mapped from 类型Key |
| 类型Key | Garmin type key | stable enum |
| 日期 | ISO `YYYY-MM-DD HH:MM:SS` | sorted **descending** by this |
| 标题 | Garmin title | often useless defaults like "XX区 跑步" (district + running); rename via `set_activity_name` when the session name is known |
| 距离km | kilometres | **rounded to 2 dp**; empty for non-running types (strength/boulder/climb/swim etc.) |
| 时长 | total time `HH:MM:SS` | whole session incl. rests |
| 移动时长 | moving time `HH:MM:SS` | pure moving |
| 平均配速min/km | `MM:SS` | **computed from moving time**; empty if not a running type or pace out of sane range (>20:00/km) |
| 热量 | kcal | |
| 平均心率 | bpm | may be empty for non-running types |
| 最大心率 | bpm | |
| 步数 | steps | |
| 累计爬升m / 累计下降m | metres | |
| 事件类型 | Garmin event type | kept as-is |
| 活动ID | Garmin activity id | **primary key**, linked to inbox filenames |

### TypeKey → Chinese mapping (keep unchanged)

```python
TYPE_CN = {
 "running":"跑步","track_running":"操场跑步","trail_running":"越野跑",
 "treadmill_running":"跑步机跑步","strength_training":"力量训练",
 "bouldering":"抱石","indoor_climbing":"室内攀岩","badminton":"羽毛球",
 "cycling":"骑行","indoor_cardio":"室内有氧","breathwork":"呼吸训练",
 "pilates":"普拉提","lap_swimming":"游泳","hiking":"徒步",
 "ultimate_disc":"极限飞盘","other":"其他"}
```

Unknown types keep their raw key as the displayed type. "Running session" (used to decide
whether to compute pace) means: `running / track_running / trail_running / treadmill_running`.

### Build / validation rules

- One row per activity, date-descending (newest first).
- Quote a value with double quotes only if it contains a comma or a quote; empty → blank.
- Historical dirty-data guard: some old rows store distance in **metres** not km
  (value > 100 ⇒ treat as metres → divide by 1000).
- **inbox holds per-session detail, the master table is the "should-have list"** —
  detail CSVs carry no date/title; they link to the master by activity ID.

## 2. Per-session detail `data/inbox/activity_<id>.csv`

Garmin's native (Chinese) single-activity detail CSV, auto-downloaded, named
`activity_<id>.csv` (`<id>` = master activity ID). Content differs by type:

| Type | Detail content | Main use |
|---|---|---|
| running / track | lap detail (time/dist/pace/HR/cadence/stride/elevation) | reconstruct splits: how many `300/100`s, fast-rep pace, rest-lap pollution |
| strength | exercises/sets/reps/weight/rest | verify sets & loads |
| bouldering | route detail | reconstruct number/grade of attempts |

Conventions:
- The directory is an **auto-generated zone**; humans must not rename or drop files in.
  The only exception: manually adding an old/missing activity and telling the agent, which
  merges it.
- Read-only, match **by activity ID** — never by timestamps or (date,distance,HR) triples
  (matching by ID since protocol v13).

## 3. Week-spec JSON (`scripts/week_spec.example.json`)

Generated by the agent from the coach package + runner profile for one week's running
sessions, consumed by `scripts/garmin_schedule.py`:

```json
{ "name": "W1",
  "days": [
    {"date": "YYYY-MM-DD", "name": "W1 Tue E5", "kind": "easy",
     "distance_km": 5, "pace_min_km": 6.9, "hr_min": 125, "hr_max": 150}
  ]}
```

Fields:
- `kind`: `easy | recovery | lsd` (limited to session kinds the profile/plan allows;
  coach-run, strength etc. do NOT go into this file)
- `distance_km`, `pace_min_km`: only for **naming and fallback duration** (easy/recovery
  execution doctrine is time + HR)
- `minutes` optional; default `round(distance_km × pace_min_km)` (30 when no distance)
- `hr_min`/`hr_max`: HR band (default 120/150)

## 4. Workout registry `garmin_workout_registry.json`

`scripts/garmin_schedule.py`'s idempotency cache: workout name → Garmin workout id.

```json
{ "W1 Tue E5": 12345678 }
```

- Runtime artifact that lives **only in the runner's private workspace** (gitignored);
  the repo ships a fabricated example only.
- Re-running the same week never duplicates workouts, only adds schedules.

## 5. Private vs repo

The repo only ships: schemas, `week_spec.example.json`, and fabricated examples. Any real
`Activities.csv`, `inbox/*.csv`, registry, and runner profile stay in the runner's private
workspace (put them under `workspace/`, which is gitignored) — never in git history.

## 6. Data pitfalls checklist (must follow when analysing)

1. **metres vs km**: historical rows may store distance in metres (>100 ⇒ divide by 1000).
2. **Judge intensity by "moving pace"**, not whole-session average: interval rest laps
   (as slow as 45:10/km) wreck averages.
3. **Interval vs continuous runs are not directly comparable**: compare full-run averages
   only within the same kind.
4. **Compare under equal conditions**: same distance + same temperature + similar HR, and
   both continuous.
5. **Cadence is read per lap**, never the whole-run "average cadence" (rest laps get
   averaged in); in FIT files cadence is single-leg → ×2.
6. **Strength CSVs contain ghost rows/sets**: cross-check with "reps × weight + rest
   column"; don't count lines blindly.
7. **Bouldering/climbing**: `时长` = whole session; `移动时长` = 0 (detail excludes
   rest/observation).
8. The master table is the "should-have list": for weekly completion analysis treat the
   master as truth; per-session detail is only for reconstructing execution.
9. **Strength-day treadmill warm-ups carry no distance**: treadmill mode **has no distance
   field**, so the warm-up never lands in Garmin as a run (you only get a "strength" record
   with an empty `距离km`).
   - **Consequence**: Garmin's weekly volume **systematically under-counts** this fixed amount
     (2 km × 2/week ≈ **4 km** in this case).
   - **Doctrine**: the figure can only come from the runner **verbally** and is an
     **estimate, not a measurement**. Mark it "verbal estimate" in the plan/log and never feed
     it into anything precise (VDOT back-calculation, pace statistics, HR-drift comparison).
   - **Review**: list the verbal amount on its **own row** when computing weekly completion
     instead of folding it into the Garmin sum — otherwise the two sides of "plan vs actual"
     use different bases.
